# 에이전트 기반 성능 최적화 연구 루프

오케스트레이터는 “어디가 느린가?”에서 시작해, 한 회차에 가설 하나를 검증한다. **아이템 성공**은 제안에서 지목한 병목을 해결했는지로 판정한다. **연구 종료**는 대표 워크로드의 주 지표가 고정 baseline을 넘어섰는지, 또는 20번째 제안까지 처리했는지로 판정한다.

## 1. Baseline과 현재 성능을 비교한다

- **무엇과 비교하는가?** 캠페인 원장에 고정 baseline과 현재 구현을 각각 식별할 수 있는 버전·설정을 적는다. 둘은 같은 버전에서 시작할 수 있다. 이후 아이템을 누적해도 캠페인의 baseline은 고정한다.
- **무엇을 개선으로 인정하는가?** 대표 워크로드, 주 지표·단위·개선 방향, 측정 범위, 입력, 환경, 반복·집계 방법, 개선 판정식을 기록한다. 프로젝트에 정한 기준이 있으면 따른다. 기준이 비어 있으면 baseline을 반복 측정해 변동폭을 파악하고 후보 측정 전에 판정식을 정한다. 정확성 검사와 허용할 회귀 범위도 이때 정한다.
- **어느 비용이 차이를 설명하는가?** 같은 조건의 baseline과 현재 구현에서 측정값과 원시 결과 경로를 남긴다. 전체 시간 중 차이가 큰 구간을 찾고 프로파일·카운터·코드 경로로 원인을 좁힌다. 관측한 사실과 아직 검증할 가설을 구분한다. 시작 시 이미 전체 개선 기준과 기능 검사를 충족하면 7단계로 간다.

## 2. 부족한 부분을 해결할 아이템 하나를 제안한다

오케스트레이터만 원장을 갱신한다. 새 제안을 시작할 때 다음 순번(`P01`~`P20`)의 항목을 먼저 저장한다. **사용한 제안 횟수는 원장에 생성된 순번 수**다. 반려와 실험 실패도 한 회로 센다. 중단된 회차는 기존 ID와 단계에서 재개한다.

제안 카드에는 다음 문장을 근거와 함께 완성한다.

> [워크로드·코드 경로]에서 [병목을 보여 주는 측정값]을 관측했다. [변경]을 적용하면 [어떤 비용이 왜 줄어드는지]에 의해 [국소 지표]가 [판정 기준]을 충족할 것이다. [대조 실험]으로 이를 확인하고, [관측 결과]가 나오면 가설을 기각한다.

직전 구현과 비교할 방법, 변경이 발동하는 조건, 확인할 기능 테스트를 카드에 적는다. 이전에 반려되거나 실패한 제안을 다시 다루면 어떤 새 증거나 설계 변경이 이전 반례를 해소하는지 밝힌다.

## 3. 다른 에이전트 세 명에게 같은 카드를 보낸다

각 리뷰어에게 제안 ID, 카드, 기준 버전, 코드·측정 근거를 함께 전달한다. 제안자와 독립된 리뷰어가 아래 질문에 각각 답한다. 세 리뷰는 병렬로 진행할 수 있다.

| 리뷰어 | 답할 질문 | 원장에 남길 결과 |
| --- | --- | --- |
| 타당성 (Soundness) | 변경이 실제 실행 경로에서 지목한 비용을 줄이는가? 비용을 타이머 밖으로 옮긴 경우나 다른 원인으로도 같은 숫자가 나오는 경우를 대조 실험으로 가릴 수 있는가? | `pass` 또는 `reject`, 판단 근거, 결정적인 측정이나 반례 |
| 기능·일반성 (Functionality) | 일반 입력, 경계값, 최적화가 발동하지 않는 경로에서 기존 동작을 보존하는가? 결과·자원 사용 등 영향을 받는 계약을 어떤 테스트로 확인할 수 있는가? | `pass` 또는 `reject`, 영향 범위, 확인할 테스트 또는 깨지는 입력 |
| 연구 기여도 (Contribution) | 성공한다면 기존 방법에 비해 무엇을 새로 설명하거나 가능하게 하는가? 어느 워크로드까지 그 주장을 뒷받침할 수 있는가? | 기여도 `high` / `medium` / `low`, 비교 대상과 근거 |

**구현 조건은 타당성 `pass`와 기능·일반성 `pass`다.** 둘 중 하나라도 `reject`면 아이템을 `rejected`로 닫고 반례를 기록한 뒤 7단계로 간다. 필수 판정이 누락됐으면 해당 리뷰부터 재개한다. 기여도는 같은 ID에 기록하며, 낮은 평가나 늦게 도착한 평가가 구현을 막지 않는다.

## 4. 승인된 아이템을 구현하고 측정한다

직전 구현에서 출발해 카드가 지정한 변경을 적용하고 diff 또는 리비전을 보존한다. 먼저 기존 기능 테스트와 리뷰어가 제시한 사례를 실행한다. 통과하면 동일 입력·환경에서 **직전 구현 대비 국소 지표**와 **고정 baseline 대비 전체 주 지표**를 측정한다. 비교에 사용한 명령, 버전, 원시 결과 경로를 원장에 연결한다. 구현 중 가설이나 적용 범위가 바뀌면 사유를 남기고 현재 회차를 닫은 뒤 7단계에서 다음 제안 여부를 결정한다.

## 5. 제안에서 지목한 병목이 해결됐는지 판정한다

| 관측 | 아이템 판정과 행동 |
| --- | --- |
| 기능 검사·회귀 기준을 위반했다 | `failed`. 실패 입력이나 회귀 수치를 기록하고 직전 채택 구현을 유지한다. |
| 유효한 실험에서 국소 지표가 카드의 기준에 미달했다 | `failed`. 예측과 실측의 차이, 다음 제안이 설명해야 할 관측을 남긴다. |
| 측정 오류나 변동으로 효과를 판별할 수 없다 | `inconclusive`. 원인과 원시 결과를 남긴다. 사전에 정한 반복을 중단했다면 같은 ID로 남은 측정을 마친 뒤 판정한다. |
| 국소 지표가 기준을 충족하고 기능·회귀 검사도 통과했다 | `succeeded`. 6단계에서 성공 기록을 남긴다. |

## 6. 성공한 아이템을 기록한다

성공 기록에는 **어떤 조건에서 무엇이 얼마나 개선됐는지** 적는다. 직전 구현과 후보의 국소 수치, baseline과 후보의 전체 수치, 기능 검사 결과, 기여도 평가, 재현 명령 및 변경 위치를 연결한다. 성공한 구현을 다음 제안의 출발점으로 삼는다. 실패·반려·판정 불가인 변경은 후속 후보에 섞지 않는다.

## 7. 종료하거나 2단계로 돌아간다

오케스트레이터는 각 회차가 닫히면 다음 순서로 결정한다.

1. **전체 성능 개선** — 기능·회귀 기준을 충족한 유효한 측정에서 대표 워크로드의 주 지표가 고정 baseline 대비 사전 판정식을 만족하면 `baseline_improved`로 종료한다. 국소 가설이 기각됐어도 전체 개선은 보고한다. 이 경우 마지막 채택 버전은 유지하고, 예상 밖의 개선을 재현할 수 있도록 측정한 후보 버전도 명시한다.
2. **제안 20회 소진** — 전체 개선을 확인하지 못했고 `P20`까지 처리했으면 `proposal_limit`으로 종료한다. 20번째 제안도 리뷰와 해당 결과 기록까지 마친다.
3. **그 외** — 최신 채택 구현과 이번 회차의 근거를 들고 2단계로 돌아간다. 예를 들어 P08에서 복사 시간이 줄었어도 전체 지연이 baseline과 동률이면, P08을 국소 성공으로 기록하고 P09에서 남은 비용을 조사한다.

리뷰어·장비·입력 부재로 해당 단계를 진행할 수 없으면 현재 ID, 마지막 완료 단계, 재개에 필요한 자원을 저장한다. 종료 보고에는 종료 사유, 사용한 제안 수, baseline과 최종 검증 수치, 성공 아이템 ID, 남은 격차, 원장 경로를 포함한다.

### 회차 원장 양식

캠페인 머리말에 1단계의 비교·판정 조건을 한 번 저장한다. 이후 각 ID의 아래 항목을 단계가 끝날 때 갱신하면, 다음 에이전트가 같은 제안을 이어갈 수 있다.

```markdown
### P__ · 아이템 이름
- 현재 단계 / 다음 행동
- 출발 버전 / 제안 카드 / 근거 경로
- 타당성 판정·근거 / 기능·일반성 판정·근거 / 기여도 평가·근거
- 변경 위치 / 재현 명령 / 원시 결과 경로
- 국소 지표(직전 → 후보) / 전체 주 지표(baseline → 후보) / 기능·회귀 검사
- 아이템 결과와 이유 / 채택 버전 / 계속 또는 종료 사유
```
