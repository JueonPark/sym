# Evaluation protocol, issue 274, version 1

Study two boundaries. The first is the execution of a compiler-produced
relocation plan under matched materialization, wire, kernel and ownership
controls. The second is a completed application request through the ordinary
frontend. On the latter, import, capture, guards, staging, the transfer and
the consumer can each change the ordering of methods.

## Fixed historical population

Retain the published November E1–E5 archive, including its assessment and
failed attempts. Re-score its accepted grid without tuning thresholds or
dropping losing cells. Use the native denominator, comparator and process
round for each original question. Treat any new tail or pairing calculation
on those records as retrospective. The focused follow-ups #263–272 have
their own frozen protocols. Link their builds, data, analysis and known
limits in the versioned catalog. A change in the machine, software revision,
admission policy, or objective starts another comparison.

- **Mechanism.** Test whether avoiding intermediate materialization helps
  under equal copy and numerical semantics, and whether changing prebuilt
  kernels on identical compiler bytes helps. Include manual and optimized
  framework alternatives. For the captured cast/permutation in #272, plot
  the original process medians for warm requests and the accounted total for
  36 calls. Keep the automatic endpoint's distinct staging and submission
  path visible.
- **Reuse and scheduling.** Compare the original dynamic sequence and held
  outputs. Report actual hits, preparations and fallbacks. The group toggle
  must keep reporting policy fixed. Use the exhaustive, same-budget #271
  oracle for planner accuracy. Distinguish cold, warm and paced objectives
  and the calibration population from held-out workloads.
- **Capacity and lifecycle.** Preserve the physical free-memory reservation,
  deployment policy, failure phase and number of attempts. Compute latency
  only over successful observations with a clear denominator. Account for
  prerequisites, first/warm requests, revisions, retirement and output
  lifetime where recorded. Report physical observations, allocator
  statistics and native ownership counters separately. Polling produces a
  lower bound on the physical peak.
- **Concurrency.** Preserve all E5 fixed bursts and their queue-inclusive
  tails. Use #271 only for the finite 40-arrival study with its declared
  deadline. A sustained-service claim would require the separate #253
  scheduler qualification with externally offered load, bounded backpressure,
  equal opportunities, fill/drain, queue waits, and throughput at a fixed
  p95 SLO. This evaluation makes an isolated completed-request claim.

## Prospective test on a pretrained application

Use a public pretrained image-classification model, real image input and a
conventional CPU tensor preparation/H2D boundary. The application protocol
and asset digests must be fixed before collecting acceptance timings.
Exercise the ordinary frontend with the existing admission policy. Include
eager and compiled Torch controls with equivalent input/output semantics and
consumer opportunities. Preserve the observed dispatch and fallback rate;
a completed fallback is a valid endpoint but cannot establish a native-path
benefit. Use fresh process rounds, paired uncertainty on completed p50 and
p95, and a separate correctness or instrumentation phase. Include first-use
and steady execution as separate results. Independent process rounds are the
units of replication. A latency ratio and a mean or median of paired
percentage changes answer different questions.

A correctness or ownership failure disqualifies a performance claim. Record
failed attempts, compile/setup costs, and the reason for any rerun. A
failure to beat the optimized control, a fallback-only result, or an
inconclusive interval narrows the claim to the observed mechanism or
workload. Publish each outcome. This one new integration extends workload
coverage on its measured GPU. Architecture comparisons require the same
workload on each device. BF16 model performance requires a separate BF16
model experiment.

## Release boundary

The source repository holds a separate issue274-v1 manifest and the new
acceptance evidence. It references the original public evidence by digest.
Regenerate historical tables and the capture-boundary figure on CPU.
Reproduce new timings separately on compatible hardware. Experiments have
different objectives and resource budgets; each reported number belongs
to one specified campaign.
